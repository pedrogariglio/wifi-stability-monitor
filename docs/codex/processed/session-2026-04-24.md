# UFW bloqueando tráfico entre containers Docker y el host

**Fecha:** 2026-04-24  
**Proyecto:** wifi-stability-monitor  
**Contexto:** Etapa 1 de observabilidad — integración de Prometheus y Node Exporter

---

## El problema

Prometheus no podía alcanzar Node Exporter en `host.docker.internal:9100`.  
El error en la UI era `context deadline exceeded` — el container intentaba conectarse pero la conexión nunca llegaba.

Node Exporter corre en `network_mode: host` porque necesita acceso a las interfaces de red reales del host para medir métricas del OS. Prometheus corre en la red bridge explícita `monitor-net`. Para que Prometheus alcance a Node Exporter, debe hacer una conexión desde la red bridge hacia el host — tráfico que UFW bloqueaba silenciosamente.

---

## Diagnóstico paso a paso

**1. Verificar que Node Exporter está funcionando en el host:**
```bash
curl http://localhost:9100/metrics | head -5
```
Si devuelve métricas → Node Exporter está vivo. El problema es de red, no del servicio.

**2. Verificar qué IP resuelve `host.docker.internal` dentro del container:**
```bash
docker exec wifi-prometheus cat /etc/hosts
```
Muestra a qué IP apunta `host.docker.internal`. En nuestro caso: `172.17.0.1`.

**3. Verificar que esa IP es alcanzable desde el host:**
```bash
curl http://172.17.0.1:9100/metrics | head -3
```
Si responde → la IP es correcta. El problema es que el container no puede alcanzarla.

**4. Verificar conectividad desde dentro del container:**
```bash
docker exec wifi-prometheus wget -qO- http://172.17.0.1:9100/metrics 2>&1 | head -5
```
Si la terminal se cuelga → hay algo bloqueando el tráfico entre el container y el host.

**5. Verificar reglas de iptables:**
```bash
sudo iptables -L DOCKER-USER -n
sudo iptables -L INPUT -n --line-numbers
```
Si `INPUT` tiene `policy DROP` y las reglas son solo de UFW → UFW está bloqueando.

**6. Verificar estado de UFW:**
```bash
sudo ufw status verbose
```
Si `Default: deny (incoming)` → todo el tráfico no explícitamente permitido se bloquea, incluyendo el tráfico desde containers bridge hacia el host.

---

## Causa raíz

UFW gestiona iptables con política `DROP` por defecto. Los containers Docker en red bridge tienen sus propias subnets (`172.17.0.0/16`, `172.18.0.0/16`, etc.) y cuando intentan conectarse al host, ese tráfico pasa por la chain `INPUT` de iptables — que UFW controla.

Docker no registra automáticamente excepciones en UFW para sus subnets. El resultado es que el tráfico container → host queda silenciosamente bloqueado.

En este servidor, UFW estaba configurado restrictivamente para WireGuard: solo SSH por `wg0` y el puerto `51820/udp` estaban permitidos. Configuración correcta para seguridad, pero que requiere habilitar explícitamente cada nuevo servicio.

---

## La solución

Permitir explícitamente el tráfico desde las subnets de Docker hacia el puerto necesario:

```bash
# Subnet del bridge default de Docker
sudo ufw allow from 172.17.0.0/16 to any port 9100 comment "prometheus -> node-exporter"

# Subnet de la red explícita monitor-net
sudo ufw allow from 172.18.0.0/16 to any port 9100 comment "prometheus -> node-exporter (monitor-net)"

# Recargar UFW para aplicar cambios
sudo ufw reload
```

Verificar que funciona desde dentro del container:
```bash
docker exec wifi-prometheus wget -qO- http://172.17.0.1:9100/metrics 2>&1 | head -5
```
Si devuelve métricas → resuelto.

---

## Cómo evitar que vuelva a suceder

Al agregar cualquier servicio nuevo que exponga un puerto y deba ser alcanzado desde un container, el checklist es:

```
1. ¿El servicio está en network_mode: host?
   → Prometheus no puede alcanzarlo por nombre de servicio
   → Necesita host.docker.internal o la IP del gateway

2. ¿UFW está activo en el servidor?
   → sudo ufw status verbose

3. ¿El puerto del nuevo servicio está permitido desde las subnets Docker?
   → sudo ufw allow from 172.17.0.0/16 to any port <PUERTO>
   → sudo ufw allow from 172.18.0.0/16 to any port <PUERTO>

4. Verificar conectividad desde dentro del container antes de asumir que funciona
   → docker exec <container> wget -qO- http://172.17.0.1:<PUERTO>
```

Regla práctica: cada vez que un servicio use `network_mode: host` y deba ser alcanzado por un container en red bridge, agregar las reglas UFW correspondientes en el mismo momento en que se define el servicio en el `docker-compose.yml`.

## Comandos de referencia rápida

```bash
# Ver estado completo de UFW
sudo ufw status verbose

# Ver subnets de redes Docker activas
docker network ls
docker network inspect <nombre-red> | grep Gateway

# Ver qué IP resuelve host.docker.internal en un container
docker exec <container> cat /etc/hosts

# Probar conectividad desde dentro de un container
docker exec <container> wget -qO- http://172.17.0.1:<puerto>

# Agregar regla UFW para subnet Docker
sudo ufw allow from 172.17.0.0/16 to any port <puerto> comment "<descripcion>"
sudo ufw reload
```

---

## Notas adicionales

- `host-gateway` en `extra_hosts` de Compose resuelve a la IP del bridge default (`docker0`), que es `172.17.0.1` — no a la gateway de redes explícitas como `monitor-net`. Esto es comportamiento esperado en Linux.
- Node Exporter en `network_mode: host` escucha en **todas** las interfaces del host, por eso es accesible tanto por `172.17.0.1` como por `172.18.0.1`.
- El diagnóstico clave es que `curl` desde el host funciona pero `wget` desde dentro del container se cuelga — esa diferencia apunta directamente a un problema de firewall, no del servicio.
